# Critic

## Summary
I checked 15 load-bearing claims against the source. 12 are confirmed and 3 refuted; the NEON-tail claim remains unclear. The 2a, 2b and 4b preconditions all hold. JSON encode and decode both run on the event loop. Upsert changes the index and counts before commit with no rollback. Cold start does a GROUP BY plus a full Python live-id set scan. require_collection reads the unlocked catalog from threadpool threads. stop() closes connections without db_lock. On PyPI, turbovec 1.0.0 is abi3-only and orjson 3.12.0 has no cp314t wheel.

What the planner must fix before writing TDD plans:
(a) The bench flag is --limit 2549619. 2,549,119 is the ingested row count, and using it forces a roughly 31-minute reingest and a different query set.
(b) 4a mislabels the arXiv corpus as 552k.
(c) Three Dockerfile designs and five briefs claiming 'ADR 0004' conflict with each other.
(d) 3a and 3b recommend opposite IVF fan-out grouping, and 3b's evidence is from AVX2.
(e) Items 1 and 3 contradict the standing constraint at ADR 0001:48 and need a superseding ADR.

Two correctness risks are missing from the briefs. First, batched sync must keep jobs 'processing' until synced, because ghost reconcile never re-adds missing vectors. Second, the native tokenizer must reproduce Python's isalnum-based `[^\W_]+`. Measured on the Windows x86-64 laptop, Python splits Devanagari where a Rust `\w` port would not.

The biggest protocol gap is that no brief measures the true-cold baseline on the freshly rebooted DGX first. The existing scratch baseline scripts should be reordered to do that before anything touches the bench volume.

Recommended order: baseline, R1 fixes, re-lock, 2b, 2a basics, item 1, IVF fan-out, batched worker, Dockerfile, FT A/B, upstream drafts.

Nothing was modified in D:\DEV\raggio or D:\DEV\_scratch\turbovec, and nothing was posted externally.

## Claim checks
- [CONFIRMED] (2a) Job payload JSON decode runs on the event loop.
  - evidence: store.py:734 `await self._process_job(json.loads(payload))` runs inside the async _run_worker. The encode side is also on the loop: enqueue (store.py:671-676) evaluates json.dumps(payload) as an argument before asyncio.to_thread runs. That makes 2a's case stronger than the brief states.
- [CONFIRMED] (2a) _upsert_rows changes the turbovec index and indexed_counts before the SQLite commit and has no rollback.
  - evidence: store.py:838-839 runs index.remove(old) and indexed_counts[...] -= 1. store.py:850 does the +1. There is a single commit at 853 and no try/rollback. _allow_cache.clear() at 854 runs outside db_lock.
- [CONFIRMED] (2a) Syncing after every job is a documented, deferred throughput lever.
  - evidence: store.py:802-803 has the ponytail comment followed by _sync_index. ADR 0001:50 lists 'batch index syncs / vacuum every N jobs' as the known ingest lever. Constraint: _run_worker (store.py:733-740) marks a job 'done' only after _process_job returns, which includes the sync. _finish_job then NULLs the payload. _reconcile_ghosts (628-648) only evicts index ids that have no DB row. It never re-adds DB rows missing from the index. Batching syncs therefore needs done-after-sync semantics.
- [CONFIRMED] (2a) IdMapIndex.remove(absent id) returns False, so it is safe to call on ids that are already gone.
  - evidence: turbovec/src/id_map.rs:516-520: 'Returns true if the id was present and removed, false otherwise'. turbovec-python/src/lib.rs:1063 returns PyResult<bool>. Caveat: _IvfIndex.remove (store.py:455-461) always returns None, so any 2a logic that relies on the return value breaks on IVF collections.
- [CONFIRMED] (2b) Cold start runs a full GROUP BY plus a full live-id scan, and records has no index to cover them. stats() runs on the event loop.
  - evidence: store.py:575-577 runs GROUP BY type WHERE indexed=1. store.py:643-644 builds a Python set of every indexed id and does a per-id int() membership loop. The only secondary index is idx_records_doc (store.py:305). app.py:146-150 calls c.stats() synchronously inside an async handler.
- [CONFIRMED] (4b) R1: the collection-auth dependency reads the shared catalog connection from threadpool threads without the catalog lock.
  - evidence: app.py:113-120 declares require_collection as a sync def, so FastAPI runs it in the threadpool, and it calls manager.get_config. store.py:1598 opens the catalog with check_same_thread=False. get_config (1630-1640) and list_collections (1650-1651) take no lock; _catalog_lock is used only at 1643, 1685 and 1726. ADR 0001 already records that concurrent statements on one connection raise SQLITE_MISUSE. The code does not show an auth bypass: hmac is still required and the failure mode is a 500. Treat R1 as a correctness/availability fix that happens to sit on the auth path, not as an auth bypass (UNVERIFIED either way without a repro).
- [CONFIRMED] (4b) R3: stop() closes connections without db_lock. R4: indexed_counts keys come only from existing types.
  - evidence: store.py:665-667 closes _read_conns and self.db outside db_lock. store.py:575-577 builds the dict from GROUP BY, so a type with no rows gets no key until store.py:850 inserts it. _bm25_rescore does sum(self.indexed_counts.values()) at store.py:1316. Under the GIL that iteration is effectively atomic. On 3.14t an insert that races the iteration can raise RuntimeError: dict changed size.
- [CONFIRMED] (4a/4b) The turbovec 1.0.0 wheels are abi3-only and cannot load on 3.14t, so a source build is required.
  - evidence: PyPI JSON (read-only, 2026-09-28): turbovec 1.0.0 has only cp39-abi3 wheels (macOS arm64, manylinux_2_28 aarch64/x86_64, win_amd64). turbovec-python/Cargo.toml:31 sets pyo3 0.29.0 with features [abi3-py39]. lib.rs:2151 has a bare #[pymodule] with no explicit gil_used flag.
- [CONFIRMED] (4a) orjson in the dev group blocks `uv sync` on 3.14t because it has no free-threaded wheel.
  - evidence: PyPI JSON: orjson 3.12.0, the latest release (uploaded 2026-08-14), ships cp310-cp315 wheels, including cp314, but none tagged 314t or 313t. It is used only by bench/bench.py:22 and bench/floor_probe.py:53. ADR 0001:31 rejected orjson as a runtime dependency, so moving it to a bench group is consistent with the ADR.
- [UNCLEAR] (3a) turbovec nq=1 goes inline below 1024 blocks and parallel above. The NEON nq<4 tail is not amortized.
  - evidence: Confirmed: search.rs:30 `SINGLE_QUERY_PARALLEL_MIN_BLOCKS: usize = 1024`, whose comment says inline is faster up to about 32k vectors. Also relevant and not cited by any brief: lib.rs:2153-2154 pins a 1-thread global rayon sentinel at module import, which affects any Python-side pool fan-out. The NEON nq=2-3 tail claim (search.rs:3717-3760) was not re-read and is UNVERIFIED. 3b's AVX2 'nq=1 pads to 4' measurement is Windows/x86 and does not transfer to aarch64.
- [CONFIRMED] (3a/3b) _IvfIndex.search probes shards serially, per query, at nq=1. Line ranges: 3a says 485-530, 3b says 504-518.
  - evidence: store.py:485-530 is the whole method. The nested loop over queries, then probed shards, then sh.search(q[1 row]) is at 504-518. Both ranges are correct at different scopes. Also confirmed for 3b: train() calibrates every shard from the same sample slice (store.py:403-408).
- [CONFIRMED] (1) The hybrid text leg's BM25 stage 2 is pure Python and holds the GIL, while the vector leg releases it.
  - evidence: _bm25_rescore (store.py:1304-1343) runs per-candidate _fold_tokens, dict tf counts, a bigram tf2 and a sort, all in Python. The hybrid gather is at store.py:1417-1420. turbovec search wraps its work in py.detach (lib.rs:639).
- [REFUTED] (2a/2b/3a/3b/4b) The arXiv bench limit: some briefs say --limit 2549619, others say 2549119.
  - evidence: Use --limit 2549619. bench/results-arxiv.md:1 reports '2,549,119 vectors', which is the ingested count: limit minus the 500 held-out queries (bench.py:83-86, header at 463). rescore_probe.py:14-15 uses gt-2549619-42-d1024.npz / N=2_549_619, and the scratch dgx-baseline.sh uses --limit 2549619. Passing --limit 2549119 changes the rng.choice query sample, forces a fresh exact-GT computation, and fails the fingerprint check, which includes limit (bench.py:379, 386-388). That triggers a full reingest of about 1879 s and gives numbers that cannot be compared with the baseline.
- [REFUTED] (4a) 4a's DGX context table describes results-arxiv as 552k x 1024.
  - evidence: results-arxiv.md:1 is 2,549,119 x 1024 (Qwen3-Embedding-0.6B). The 552,515 x 1536 corpus is the email bench (ADR 0001:5-6, bench/results.md).
- [REFUTED] (1/3a) Items 1 and 3 fit inside the accepted ADR 0001 constraints.
  - evidence: ADR 0001:48: 'turbovec is an external dependency — kernel changes (SIMD, ANN, multi-partition search) are out of scope; everything layers on IdMapIndex.' ADR 0001:49 names ANN-in-kernel, more CPUs or free-threaded Python as the only remaining headroom. Item 1 adds a first-party Rust extension, and item 3 proposes upstream kernel/ANN work. Both need a new ADR that explicitly supersedes 0001:48 in part. Also stale: ADR 0001:33 ('ghost reconciliation Rejected (no API)') predates _IvfIndex.all_ids (store.py:532-535).

## contradictions
- Fan-out grouping. 3a recommends plain per-(query, shard) nq=1 fan-out with no audience grouping, because the aarch64 NEON nq=2-3 tail is not amortized. 3b recommends audience-batched plus pooled fan-out, based on AVX2 (Windows x86-64 laptop) numbers where nq=1 pads to 4. The two are mutually exclusive, and 3b's evidence comes from the wrong ISA for the DGX.
- Root cause of the DGX IVF latency. 3a blames roughly 31 ms of non-kernel per-query overhead; 3b blames the serial per-shard drain. They imply different fixes, and neither was attributed on the DGX with a stage probe after the reboot.
- Three incompatible Dockerfile rewrites. Item 1: two-stage uv:python3.12-bookworm-slim with rustup. Item 4a: ARG PYTHON, a rust:1-slim-trixie builder and a debian:trixie-slim runtime. Item 4b: ARG PYTHON_VERSION in the main Dockerfile plus a separate Dockerfile.ft on uv:bookworm-slim / debian:bookworm-slim. The current Dockerfile is single-stage uv:python3.12-bookworm-slim.
- 4a rejects a separate Dockerfile.ft (its option C) and 4b proposes exactly that.
- 4a says the bookworm uv image tags are frozen at 0.9.30. 4b's Dockerfile.ft and item 1's builder still base on bookworm uv tags. If 4a is right, both of those designs pin an old uv (UNVERIFIED: registry tags not queried).
- ADR number collision: items 1, 2a, 2b, 3a and 4a/4b each claim 'ADR 0004'. docs/adr currently holds 0001-0003.
- Bench limit: 2a and 3a use --limit 2549619; 2b, 3b and 4b use --limit 2549119; 3a uses both. Only 2549619 reproduces the published query set, ground truth and ingested volume (see claim check).
- 4a's context table mislabels results-arxiv as 552k x 1024. The correct figure is 2,549,119 x 1024.
- A partial index on jobs(status) appears twice, as 2a T9 and 2b T5. If both land, they risk two index definitions or a merge conflict in open_meta_db.
- Measurement protocol: 4a runs --reingest on every ABAB run (about 31 min of ingest each at 1879 s per 2.55M). 4b reuses the ingested volume. These give different cold-start and page-cache conditions. results-arxiv.md:32-35 already rejected reuse-path cold-start numbers as flattering.
- Several briefs vs the accepted ADR 0001:48: items 1 and 3 break the 'kernel changes out of scope / everything layers on IdMapIndex' standing constraint without proposing a superseding ADR, and each claims an ADR number that collides with the others.

## cross_item_dependencies
- Store.py hotspots edited by several items, so they need an agreed merge order. _vector_ids / _allow_cache (store.py:1178-1191) is touched by 3a (sorted cache), 4b R2 (generation counter) and 2b (np.fromiter). _IvfIndex (362-535) is touched by 3a/3b (fan-out), 2a T6 (dirty-shard sync) and 4b R2b (id-cache generation). stop() (655-669) is touched by 4b R3 and 2a's batched flush. indexed_counts (575-577, 838-850) is touched by 4b R4 (pre-seed) and 2a (move updates after commit).
- The claim query: 2a's claim cursor (`id > ?`) must keep the literal `status IN ('pending','processing')` predicate, or SQLite will not use 2b's partial index. resume_pending (store.py:1735-1737) and pending_jobs (690-693) use the same text and must stay consistent.
- Item 1 depends on 2a and 4b R4: _bm25_rescore takes N from sum(indexed_counts.values()) (store.py:1316), and avgdl/df come from the caches. Settle the indexed_counts ordering and pre-seed changes before generating item 1's parity goldens. Better, make the native function take (idf, avgdl, norm constants) as inputs so parity is a pure-function property.
- Item 1 and item 4. The native extension must build without abi3 and declare gil_used=false, or it re-enables the GIL on 3.14t. 4b's cp314t verification assumes this. Python 3.14's unicodedata tables differ from 3.12's (exact version UNVERIFIED; the laptop's 3.13.15 reports 15.1.0), so the Python fallback tokenizer can change between the 3.12 and 3.14t arms. That confounds 4's text-hit A/B and 1's fallback parity tests.
- Item 4 and item 3 upstream work. 3.14t requires a non-abi3 source build of turbovec, because Cargo.toml:31 hardcodes abi3-py39. Until upstream publishes cp314t wheels, item 4 means carrying a patched build. Put the cp314t-wheel request in the same upstream draft set as 3's ANN/partition asks.
- The uv upgrade and re-lock (4a) should land before item 1 re-locks for its native extra, and before any group change for orjson. pyproject.toml and uv.lock will conflict otherwise. Give the lock a single owner.
- Fan-out (3a/3b) and FT (4). A Python-side thread pool plus 3.14t plus turbovec's pinned 1-thread global rayon sentinel (lib.rs:2153-2154) can oversubscribe or serialize in combinations no brief measures. Measure fan-out on 3.12 first, then again on 3.14t.
- 2a's binary job payload and crash replay. Jobs already journaled as JSON TEXT by the old version must still decode after the upgrade, so the replay path must accept both formats (mixed journal after an in-place upgrade).
- 2a's batched sync and 4b R3. The final flush must happen in stop() under lock.write() and before connections close. R3's locking change must include the flush, or shutdown can lose the last batch.
- 2b T6 (Collection() construction in to_thread) and CollectionManager. It interacts with _load_lock (an asyncio.Lock) and with asyncio primitives created in Collection.__init__, which must be bound or created on the loop. It also changes where R1's catalog reads happen.
- 4b R1 is independent of every other item and can ship first.

## gaps
- No unified baseline session after the reboot. The fresh reboot is the only chance to measure a true cold page cache. Each brief assumes its own baseline, and none says to measure cold start first. Scratch already has D:\DEV\_scratch\dgx\dgx-baseline.sh and dgx-baseline2.sh, written for an earlier reboot, but they run `uv sync` and `podman build` first and start bench-tv before recording anything. Unknown after this reboot (agents have no DGX access): whether bench-tv restarted automatically (which would already spend the cold window and replay jobs), and whether vLLM is up. dgx-baseline2.sh shows a replayed attach_index job (10201) left pending by an earlier session. resume_pending replays it on boot, which pollutes both cold start and early latency.
- Baseline order the plan should fix, all on image 19a8a2e recorded by digest, with git SHA, turbovec version and host facts. (1) uptime, free -g, podman ps and podman stats, before anything else. (2) First container start: time to healthz and to first query. (3) Wait for pending_jobs=0. (4) Stage and shard-call probes. (5) Bench run1/run2 with --limit 2549619 and no --reingest, keeping run1 vs run2 as the noise band. (6) If 2a needs ingest numbers, one --reingest run last, because it rewrites and compacts files.
- Warm vs cold is not separated. The reuse path and the detach/attach cycle between the raggio and raggio-ivf engines compact files and warm the page cache. results-arxiv.md:32-35 and the ADR 0003 audit already flag these as flattering. Every item's cold-start claim must come from a first start after the page cache is dropped or the host rebooted, not from within an ABAB session.
- Anti-benchmaxxing in the style of ADR 0003. Tunable constants must be chosen on an independent sample (seed 7, following text_probe.py) and published on seed 42: fan-out pool size and grouping gate (3), batch-sync N/T (2a), candidate depth and any BM25 constants touched by item 1. The concurrent phase repeats the same 500 queries, which warms the allowlist and df caches. Report a no-repeat variant or disclose it. Only claim wins that exceed the run1/run2 noise band. The perturbed-query column (ADR 0003) is still missing, and item 1 must not change ranking at all.
- Item 1 tokenizer parity is under-specified. Python `[^\W_]+` (store.py:185) uses str.isalnum semantics, and _fold (175-181) uses Python's unicodedata. Rust regex `\w` also matches combining and spacing marks. Measured on the Windows x86-64 laptop (not the DGX), Python 3.13.15, Unicode 15.1.0: 'हिन्दी' tokenizes into 3 single-consonant tokens in Python, where a naive Rust `\w` port yields 1. The golden set needs Indic and other Mc/Mn scripts, CJK, NFKD compatibility characters, underscores and digit categories, with the Unicode version pinned. Score parity also needs a defined tolerance and identical tie-breaks: sort key (-score, rid) at store.py:1340, plus summation order.
- Batched sync crash semantics are missing from 2a. Today 'done' implies synced, and replay is the only recovery for committed-but-unsynced rows, because _reconcile_ghosts never re-adds missing vectors. If jobs are marked done and their payloads NULLed before the covering sync, a crash silently leaves indexed=1 rows with no vector. There is no detector for that direction.
- 2b does not measure the ingest cost or meta.db growth of the wider covering index at 2.55M rows. It also does not measure the one-time CREATE INDEX cost on first open of an existing collection, which becomes a cold-start regression exactly once.
- No brief measures combined effects: item 1 on 3.14t, 3's pool on 3.14t, 2a's batching together with 3's fan-out under concurrent ingest plus search.
- No CI. .github/workflows holds only docs.yml. Nothing enforces the native-vs-fallback parity tests, the 3.14t GIL guard (PYTHONWARNINGS error on GIL re-enable), or the R1-R4 stress test.
- The laptop-vs-DGX transfer is not addressed. 3b's AVX2 evidence and any Windows timing cannot predict GB10 NEON behavior. Every performance decision needs a DGX A/B, labeled as such.
- Upstream drafts (3) are not tied to a measurable raggio-side acceptance criterion. Neither the cp314t wheel request (4) nor the nq<4 NEON tail (3a, UNVERIFIED) has a scratch repro attached.

## user_decisions
- Dockerfile strategy. Recommended: one Dockerfile with ARG PYTHON (default 3.12) and a Rust builder stage. No separate Dockerfile.ft. Before choosing between bookworm and trixie bases, check whether the bookworm uv tags really stopped at 0.9.30.
- ADR numbering. Recommended: 0004 native BM25 (item 1), 0005 IVF fan-out and the upstream stance (item 3, partly superseding ADR 0001:48), 0006 free-threading (item 4). Item 2 changes go into an ADR 0001 addendum, except batched sync, which changes the lever recorded at 0001:50 and should be noted there.
- Fan-out grouping (3a plain nq=1 vs 3b audience-batched). Recommended: decide only from a DGX A/B. Default to 3a's plain fan-out, and put 3b's batching behind a gate that ships only if it beats the noise band on aarch64.
- Whether R1 ships as a standalone fix before everything else. Recommended: yes. Describe it as a correctness and availability fix (a shared SQLite connection used from threadpool threads), not as an auth bypass.
- orjson: move it or bump it. Recommended: move it to a `bench` dependency group, excluded from the default sync, and do not bump. There is no cp314t wheel as of 3.12.0, and ADR 0001:31 already keeps runtime JSON on stdlib.
- Timing and status of free-threading. Recommended: evaluation-only experimental image after items 1-3 land. Do not make 3.14t the default until turbovec publishes cp314t wheels upstream, so raggio never maintains a turbovec fork build.
- Posting upstream turbovec issues. Recommended: agents prepare drafts with scratch repros, and the maintainer reviews and posts them personally.
- Failure policy for batched sync. Recommended: a job stays 'processing' with its payload kept until the covering sync lands. Bound batches by N jobs or T seconds, flush in stop(), and rely on the existing replay for crashes.
- Covering-index migration. Recommended: measure CREATE INDEX time at 2.55M rows first. If it takes more than a few seconds, document it as a one-time cold-start cost in release notes rather than building it lazily in the background.
- Tokenizer parity policy for item 1. Recommended: the native tokenizer replicates Python's current `[^\W_]+` plus NFKD-fold semantics exactly, including the odd Indic splitting, so item 1 changes no ranking. Any move toward FTS5 unicode61 semantics becomes a separate, measured change.
- CI. Recommended: before items 1 and 4 merge, add a minimal test workflow (3.12 with both native and fallback paths, plus a non-blocking 3.14t job with the GIL-guard warning set to error).
- Whether to spend the true-cold window now. Recommended: yes. Run the cold-start and baseline capture on the just-rebooted DGX before anything else touches the bench volume, and record whether bench-tv restarted automatically.
