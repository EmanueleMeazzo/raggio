# DGX probe p1 — cold start, SQLite indexes, memory release (2026-09-28)

This probe was run on gn100 (GB10, SQLite 3.40.1, glibc 2.36, image `localhost/raggio:baseline` at 19a8a2e), 03:44–05:50 CEST. The collection is `bench`: 2,549,119 chunks, 1 chunk per doc, 0 ghosts. meta.db is 15,132.6 MB, and the records table is about 3.57 GB.

Raw logs and scripts are in `D:/DEV/_scratch/dgx-probes/p1-coldstart-sqlite-memory/{logs,scripts}`, mirrored at `~/probe/p1-coldstart-sqlite-memory/` on gn100. The Plan C code measured here is a **prototype** generated by `scripts/mkplanc.py`, not the final plan code.

**Terms used in this report:**

- **true-cold:** the data-dir files are evicted with `posix_fadvise(DONTNEED)`, and eviction is verified with `fincore`. This validates spec D12.
- **warm:** host page cache.
- **4g:** `--memory 4g`. On gn100 this also grants up to 4 GiB of swap, because the host has a 16 GiB swap file. `--memory-swap 4g` is the swapless case.

### Memory (finding 4)

**Default glibc, warm, 4g, with host swap:**

- attach1 peaks at VmHWM 4,105 MiB, the cap, with up to 634 MiB swapped.
- RSS after the job is 3,032–3,064 MiB.
- The detach and the second attach are **refused** by `_require_headroom`: 1,030–1,062 MiB free against a need of 1,372 / 1,884 MiB.

**Swapless (`--memory-swap 4g`), default glibc:**

- `POST /index` is **OOM-killed** during stream+add (kernel memcg OOM, anon-rss 4.18 GB, exit 137).
- `malloc_trim` alone is killed the same way.
- In both runs `_require_headroom` **passed** beforehand.

**`MALLOC_TRIM_THRESHOLD_=134217728`, swapless:**

- attach1 HWM 3,642 MiB, no swap. RSS after attach1 1,832 MiB.
- detach passed (25.9 s); attach2 passed (52.0 s).

**Best result: `MALLOC_TRIM_THRESHOLD_=134217728` + `malloc_trim(0)` after each job, swapless:**

| Point | RSS / HWM |
|---|---|
| loaded | 1,455 MiB |
| attach1 peak (HWM) | 3,631 MiB |
| after attach1 + trim | 1,707 MiB (trim took 0.007 s) |
| after detach | 1,506 MiB |
| after attach2 | 1,662 MiB |
| final HWM | 3,646 MiB |

That leaves about 450 MiB of slack under the cap.

**`MALLOC_ARENA_MAX=2`:** no benefit, and 10–20 % slower builds (57–63 s).

**Guard vs reality:**

- The guard's build "need" is 1,884 MiB.
- Measured growth over loaded RSS is 2,176–2,186 MiB with trimthr, and about 3.0–3.1 GiB (RSS + swap) with default glibc.
- Cold refusals wasted 139 s (detach) and 194 s (attach2) of backfill/COUNT pre-work before the guard ran.

## Conclusions

1. **Plan C cold start.** Container start → first GET takes about 4.3 s on IVF and about 3.3 s on flat, against 120–125 s at the baseline. `/healthz` stays ≤ 3 ms, and the cold read volume falls from 8.5–8.8 GB to 1.4–1.7 GB.
2. **The published 28–30 s cold start is not a true-cold number.** Baseline true-cold at 4g is 120–125 s, and warm is 4.6–5.4 s.
3. **Under a 4 GiB cap every `GET /collections/{name}` takes about 41 s and blocks the loop.** This is a larger user-visible bug than the first-load one. Plan C brings it to 0.55–0.59 s.
4. **D9: CREATE INDEX is not "a few seconds".**
   - It takes 40.8 s true-cold and 1.73 s warm, about 16 s per 1M chunks cold.
   - It is a one-time migration inside `open_meta_db`/`Collection()`, so it must run off the loop, with progress logged.
   - It needs a release note.
   - The first cold open after the upgrade is estimated at about 46–47 s. That is the sum of measured parts, not an end-to-end measurement.
5. **The covering index needs a planner fix** on the sorted listing: `NOT INDEXED` or unary `+type`/`+indexed`, plus an EXPLAIN-plan regression test. `ANALYZE` does not fix it.
6. **Adopt the numpy reconcile, rowid `_vec_sample` and `idx_jobs_open`.** Rowid sampling needs an `ORDER BY RANDOM()` fallback when `n / MAX(id) < 0.2`.
7. **Memory release:**
   - Set `ENV MALLOC_TRIM_THRESHOLD_=134217728` in the image.
   - Call `malloc_trim(0)` (ctypes, glibc only) after each index job.
   - Do not use `MALLOC_ARENA_MAX=2`.
   - The **release gate is a swapless 4g run** (`--memory-swap 4g`): `POST /index`, `DELETE /index`, `POST /index`, with no OOM and VmHWM ≤ 3.8 GiB.
8. **Headroom guard:**
   - Run it **before** the backfill/COUNT pre-work.
   - Raise the attach need to the measured growth (about 2.2 GiB with trimthr).
   - It compares `memory.max − VmRSS` and ignores swap, so it cannot be the only protection. It passed before both OOM kills.
9. **Cold attach path.**
   - `_backfill_vecs`' LEFT JOIN is still `SCAN r` after the covering index. Together with COUNT it costs 178 s cold.
   - Fix: use an anti-join over the covering index, or skip the backfill when `COUNT(vecs)` equals the indexed count.
   - Stream+add reads records by rowid (170 s cold). The swap live-set scan (55 s cold) should use the covering index.
10. **Metadata-filtered and metadata-sorted listings** still scan the 3.57 GB table under 4g (43–51 s cold per request). Plan C does not address this. A follow-up could add an expression or generated-column index.

## Plan C DGX acceptance thresholds

These run on gn100 at 2.55M, `--memory 4g`, true-cold unless stated. The measured prototype value is in brackets.

1. **Cold start:**
   - start → first GET: IVF ≤ 6 s [4.32], flat ≤ 5 s [3.34]
   - first search: IVF ≤ 5 s [3.24], flat ≤ 4 s [2.26]
2. **`/healthz` max during a cold load:** ≤ 0.1 s [0.003]
3. **Later GET under 4g:** ≤ 1.0 s [0.55–0.59]
4. **`Collection()` cold read:** ≤ index size + 150 MB [1,722 / 1,433 MB]
5. **Migration:**
   - CREATE INDEX ≤ 60 s cold [40.8] and ≤ 3 s warm [1.73]
   - meta.db growth ≤ 120 MB [+96]
6. **`_vec_sample`:**
   - k = 65,536: ≤ 15 s cold [8.05], ≤ 1 s warm [0.39]
   - k = 1,024: ≤ 1 s cold [0.23]
7. **Reconcile diff:** ≤ 0.1 s [0.02]
8. **Swapless memory run** (4g + `--memory-swap 4g`, POST → DELETE → POST index):
   - no OOM
   - both second operations pass the guard
   - attach VmHWM ≤ 3.8 GiB [3.63–3.67]
   - post-job RSS within 0.5 GiB of loaded
   - warm attach ≤ 70 s [52.0]
   - detach ≤ 35 s [25.9]
9. **Listing:**
   - warm "list page sorted chunks" ≤ 1.0 s [0.76 with `NOT INDEXED`]
   - list count chunks ≤ 0.2 s warm, ≤ 1 s cold
10. **Cold `POST /index` (not measured with Plan C):**
    - pre-work ≤ 10 s [baseline 178]
    - `vec_sample` ≤ 15 s [baseline 152]

## Caveats

- **Sample sizes.** Many figures are n=1: every memory variant, the cold IVF build, the first-search cold starts and the cold list timings. The baseline server cold start is n=2.
- **Eviction scope.** Only the data directories were evicted. The image layers and Python stayed host-cached. "Warm" means the host page cache, not memory owned by the container cgroup.
- **Not measured:**
  - a Plan C cold IVF build;
  - migration + load end-to-end in the server;
  - the CREATE INDEX RSS footprint;
  - `MALLOC_MMAP_THRESHOLD_`;
  - behaviour beyond 2.55M rows.
- **Source of the mechanism.** The explanation of how `MALLOC_TRIM_THRESHOLD_` works (it disables the dynamic mmap threshold) comes from glibc documentation. The probe measured only the effect.
- **Unexplained:**
  - base-cold's first GET took 150.4 s, against 119–125 s in the other runs;
  - cold single-query scans took 43–51 s standalone, against 38–40 s inside load.py.
- **Cleanup.** The DGX was left clean: no probe containers or images remain, `~/probe/data-ivf` is untouched, and bench-tv is stopped.
